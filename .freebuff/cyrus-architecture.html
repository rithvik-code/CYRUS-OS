CYRUS OS — Visual Architecture

One brain, two interfaces, agents underneath — how every piece connects.

The core idea: CYRUS is an AI-native operating environment — you speak in intent, and it plans, checks permissions, acts, and verifies. The GUI and the CLI are just two windows into the same brain: neither contains its own intelligence, and every action funnels through one policy gate and one audit log.

§2 · The mind

Inside the brain: intent → plan → verify

Every request — from the chatbot, the palette, or the terminal — is decomposed the same way. The confirmation step is not optional: the planner must never execute destructive operations blind.

🧠 What the brain holds

Intent engine“find my java assignments” → search_files + filters. Hallucinated intents are rejected — only whitelisted verbs exist.
PlannerBreaks the intent into steps, checks risk, orders execution, verifies results, reports back.
ContextLive injection: open windows, folder sizes, recent actions — every AI call sees the real OS state.
MemoryPersistent facts (“remember that …”) in ~/Memory, re-injected into every conversation.

§3 · Interface one

The CLI: classic commands + natural language

The terminal keeps every traditional command (cd, ls, git, pip — ~110 builtins) and layers natural language on top. Neither mode is special: both are front-doors to the same brain.

§4 · Interface two

The GUI: intent-first desktop

The desktop is built around one question — “what do you want to do?” — answered by the palette (Ctrl+Space), the chatbot, or the Start menu. Every path reaches the same intent engine.

✨ Ask CYRUS…

Topbar search + palette: type an intent, get a ranked action — never a settings hunt.

☀️ Daily briefing

Proactive once-a-day brief from real OS state; the AI watches so you don't have to.

🎛️ Workspaces

“start my college workspace” restores the exact windows and folders for that context.

🪄 App Maker

Describe a mini-app, CYRUS builds and sandboxes it into Start → My Apps.

🎨 Generative themes

“A candlelit library at midnight” → palette, wallpaper and orbs recomposed.

🎙️ Voice

Mic dictation in, spoken replies out — the keyboard becomes optional.

§5 · CLI ↔ GUI

One brain, two faces — fully connected

The killer detail: the interfaces talk to each other through the core. “Open a terminal here” from the GUI opens it in the right folder; “open this folder visually” from the CLI opens Files. Cross-navigation is a first-class intent.

⌨️ CLI

  • ai <request> — intent → action
  • ask <task> — AI writes the command
  • open this folder visually
  • full classic command set + git + docker
⇄

🖥️ GUI

  • Palette: Ctrl+Space “find my java assignments”
  • “Open a terminal here” → shell at that folder
  • Files ranked search from any surface
  • Chatbot with 🧠 memory + voice

Same flow both ways: input → intent engine → policy gate → whitelisted action → audit log → result rendered in whichever window asked.

§6 · Local + cloud

The AI router: free-first, key-optional

No provider lock-in. Tasks are classified (reasoning / fast / vision / general) and routed down a lane of providers; the first that answers wins. A pasted OpenAI key jumps every queue; local rules always catch the fall.

§7 · Trust

Permission system: risk-classified, human-gated

The model never receives raw shell access. It emits whitelisted intents; a static policy table classifies each; humans confirm anything destructive. Every step lands in the audit log (Memory app).

RiskExamplesBehavior
LOWSearch files · open apps · read files · system info · chatRuns immediately, logged
MEDIUMMove files · organize folders · install packages · change settingsConfirmation dialog → then runs
HIGHDelete trees · modify system files · privileged commandsBlocked outright — or requires explicit typed confirmation with undo staged

Error recovery is part of the policy: failures come back explained (“pandas is missing — requirements.txt found → [Install]”) instead of raw tracebacks. Terminal explain <cmd> pre-warns before you even run a thing.

§8 · The path

Roadmap: environment first, kernel never (until it matters)

Don't build a kernel to prove a point. Ship the AI-native environment on an existing base, then — only when the layers above are stable — consider a Linux-derived bottom layer.

Stage 0 · Browser port SHIPPED

Desktop, WM, dock, terminal (~110 cmds), Files, Studio IDE, AI Studio, router, policy engine, memory, briefing, App Maker, themes, organizer.

Stage 1 · Life & productivity IN PLAN

Calendar, Reminders, Photos, Media, Camera, Contacts, Print/PDF, Import/Export + Backup, Trash — the daily-use surface.

Stage 2 · Desktop completeness NEXT

Right-click everywhere, drag & drop, Aero Snap, real virtual desktops, widgets, quick settings, clipboard history, session restore.

Stage 3 · Grandma-simple NEXT

Multi-user profiles, Simple Mode (huge tiles, voice-first), guided tour, global undo, accessibility.

Stage 4 · Real base LATER

The same Brain/CLI/GUI/Agents architecture, re-hosted on a Linux base with real filesystem and process control — the interfaces never change, the kernel does.

CYRUS = you → AI → applications → files → OS.
